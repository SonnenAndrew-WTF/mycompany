# Контекст проекта mycompany (lsFusion)

МК — сокращённое название проекта mycompany.

## Репозитории

- Основной репозиторий доработок: `rokotoff/mycompany` (fork `lsfusion-solutions/mycompany`).
- Остальные участники работают в своих fork от `rokotoff/mycompany` и присылают изменения через pull request.

## Чьи папки (`src/main/lsfusion`)

- `extra` — доработки владельца репозитория (rokotoff). Верхний модуль — `MyCompanyExtra`.
- `alfaExtra` — доработки второго разработчика. Верхний модуль — `AlfaExtra`, он подключает `MyCompanyExtra`.
- `custom` — ведёт другая команда, не изменять.
- Остальные папки — код upstream (`lsfusion-solutions/mycompany`), не изменять.

Работай только в своей папке. Чужие модули можно читать и использовать через `REQUIRE`, но не изменять.
Новый модуль подключай в `REQUIRE` верхнего модуля своей папки.

## Клиентский JS и CSS (`src/main/resources/web`)

- Базовые `.js` / `.css` из upstream и custom не изменять. Поведение меняется надстройкой: свой скрипт оборачивает глобальную функцию вида (`window.comments`) или расширяет `window.Quill`, как `commentMentions.js` (custom) и `commentImages.js` (extra).
- Свои файлы — в `web/<папка своих доработок>/` (например, `web/extra`), подключение — `onWebClientInit('<файл>') <- N` в своём модуле, с порядком больше, чем у оборачиваемого файла.
- `onWebClientInit` ищет файл по имени без пути, поэтому имена файлов должны быть уникальны во всём `web/`.
- Порядок загрузки скриптов комментариев: `comments.js` — 2, `mentions.js` — 3, `commentMentions.js` — 4, `commentImages.js` — 5.
- Доска распределения работ (`extra/planning`): `workboard.js` / `workboard.css` — 6, диаграмма Ганта `workgantt.js` / `workgantt.css` — 7 (использует помощники из `workboard.js`).

## Формы с custom-представлениями (опыт доски распределения и Ганта)

- Горизонтальный контейнер в `DESIGN` по умолчанию переносит элементы на новую строку: для раскладки «список слева, доска справа» нужен `wrap = FALSE`.
- `fill = 0` не только фиксирует ширину, но и отключает растягивание по высоте. Чтобы ширина была фиксированной, а высота — на весь контейнер: `flex = 0` и `alignment = STRETCH`.
- Большое custom-представление (десятки колонок или плашек) раздувает контейнер формы по своему содержимому. Тело представления позиционировать абсолютно внутри `position: relative`, прокрутку делать внутри.
- Действие, которое JS вызывает через `controller.changeProperty`, должно быть колонкой группы (`GRID`), иначе оно ищется на уровне формы и не находится.
- Один фильтр на двух вкладках формы — одно и то же свойство, добавленное на форму второй раз под другим именем (`PROPERTIES() ganttResponsible = nameFilterResponsible`).
- Выбор из нескольких вариантов платформа рисует рядом кнопок на всю ширину. Выпадающий список — в `DESIGN`: `MOVE PROPERTY(...) { select = 'dropdown'; }`.
- Выбор объекта только из подходящих: `INPUT t = prop() CHANGE LIST name(t) WHERE cond(t)` в обработчике `ON CHANGE` свойства на форме.
- `COLOR` в `JSON FROM` приходит числом ARGB, часто отрицательным. В JS цвет для CSS: `'#' + ((c >>> 0) & 0xFFFFFF).toString(16).padStart(6, '0')`.
- Действие с параметром объекта в блоке `PROPERTIES` без заголовка само колонкой группы не становится — дописывать `GRID` (`PROPERTIES calPick = calendarPick(cd) GRID`). Иначе `changeProperty` падает с ошибкой `names no property of the form level`.
- Выражение периода формы (`periodFrom()` / `periodTo()`: `CASE` по дню / неделе / месяцу на локальных свойствах) внутри агрегатов по дням (`GROUP SUM ... IF iterate(d, ...)`) даёт `TOO LONG QUERY`. Границы копировать в `DATA LOCAL` событием `WHEN LOCAL FORMS <форма> CHANGED(periodFrom()) ...` и считать по ним. Событие с `FORMS` писать после объявления формы.
- Редактируемая строка с `NULL` в таблице показывает «Не определено» — убрать `placeholder = ''` в `DESIGN`. Выбор «пусто = все активные» — выпадающий список статусов с `placeholder = 'Активные'` (фильтр «Статус заказа» на досках).
- Свои действия из JS, которые меняют распределения, делать парой: внутреннее без `NEWSESSION` (`moveIn`, `splitIn`, `allocateIn`, результат — в `DATA LOCAL`) и обёртка с `NEWSESSION ... APPLY`. Групповые действия (звено) вызывают внутренние в цикле в одной сессии.

## Правила

- Перед работой с lsFusion используй `lsfusion_get_guidance`.
- Пока метакод в IDE свёрнут, диагностика подчёркивает как ошибки свойства, которые он создаёт (у производственного заказа — `number`, `scheduledDate`, `readonly`, `nameStatus`, `colorStatus`). Это не ошибки кода: проверяет запуск сервера.
- Локальные настройки сервера — `conf/settings.properties`, он не хранится в git. Шаблон — `conf/settings.properties.example`.
- Личные настройки участника — в `CLAUDE.local.md` (не хранится в git).

## Как присылать изменения

- Каждая задача — отдельная ветка от свежего `master`; перед началом подтянуть изменения из `rokotoff/mycompany`.
- Pull request в `rokotoff/mycompany` с описанием: что сделано, на что обратить внимание при выкладке, как проверено.
- В upstream (`lsfusion-solutions/mycompany`) ничего не отправлять — ни push, ни pull request.
- `gh pr create` вызывать с явным `--repo rokotoff/mycompany --base master`: для fork без `gh repo set-default` gh может выбрать родительский репозиторий, то есть upstream.

## Выкладка на рабочий сервер

- На рабочем сервере `logics.topModule = AlfaExtra` — он подключает `MyCompanyExtra`, поэтому загружаются обе папки доработок.
- Проверить, что новые файлы из `src/main/resources/web` попали в jar; после выкладки изменённого JS пользователям обновить страницу (Ctrl+F5).
- Доски распределения: после первой выкладки завести доски в «Производство → Настройка → Настройка досок распределения», без них форма «Доски распределения» пустая.
- Гант меняет сроки в самих производственных заказах (дата начала, плановое завершение) — те же поля, что в карточке и списке заказов.
- Этап 3 планирования: звенья заводятся в «Производство → Настройка → Звенья» или собираются на доске («Собрать звено»). В «Настройках» появился «Допуск расхождения план/факт, ч» (по умолчанию 2). Новые таблицы `workTeam`, `workTeamEmployee`, `workAbsence`, новые поля в `workAllocation`.
- Если фильтры по статусам документов показывают лишнее (например, «Активные» показывают выполненные заказы), выполнить пересчёт материализаций: «Администрирование → Обслуживание».

## Особенности проекта

- Включён перевод строковых литералов (`logics.lsfStrLiteralsLanguage`): короткий литерал может замениться переводом из словаря (например, `'s'` становится кириллическим `'с'`). Коды и ключи не склеивать из коротких литералов — писать их целиком.
- Тестовые данные заливать скриптом через `/eval/action`, а не отдельным модулем. Кириллицу в скрипте передавать из файла.
- Картинки в комментариях (модуль `CommentImagesExtra`) хранятся внутри текста комментария как `<img src="data:image/...;base64,...">`. Код, который обрабатывает текст комментария (письма, упоминания, поиск, выгрузки), должен это учитывать.
- Производственный заказ: тип обязателен; статус «Готов» требует склад материалов, «Выполнен» — склад продукции.
- В рабочей базе номер производственного заказа — описательный текст («Бондюэль\З-15\Тросовый транспортер»), наименование изделия обычно пустое. Плановое завершение — `planeDateTime` (модуль `ManufacturingOrderExtra`).
- Справочник должностей общий для сотрудников и контактов контрагентов. В выборе для сотрудников показывать только должности, назначенные сотрудникам.
- Пустая строка в lsFusion — не `NULL`, а `toDateFormat('')` возвращает `0001-01-01`. Значения из JS (даты, строки) проверять на пустую строку явно.
- Табель (`TimeEntry`) — основа зарплаты (`ProjectTimeEntryPayslip`, `PayslipBatchExtension`) и «Генерации руб/час» заказа. Планирование табель только сравнивает и не меняет. Обычный день в табеле — 12 ч (кнопка часов), норма плана — 10 ч.
- Копия рабочей базы на локальном сервере: до первого запуска отключить автозапуск планировщика, активные задачи планировщика и токены ботов (Max) — иначе локальный сервер начнёт делать бэкапы по путям рабочего сервера и писать от имени бота.
